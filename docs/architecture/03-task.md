# 模块三：Task

调研日期：2026-09-12。todo 与 compact 属于本项目规划；自动定时调度作为架构回答，不纳入第一版必要功能。

## 1. 长程任务执行一段时间忘记目标，怎么办？

面试回答：把目标和工作状态放在模型之外，以可验证状态驱动循环。prompt 提醒有帮助，但不能代替持久化、预算和验收。

| 方案 | 优点 | 代价及失败模式 |
| --- | --- | --- |
| todo 工具 | 显式子任务、进度易检查，可恢复 | 容易形式化打勾；必须把完成与证据关联 |
| plan 模式 | 先对齐依赖与验收，再执行 | 计划可能过时；需处理用户增改，不是永不变的脚本 |
| /goal 持久目标 | 每个关键边界检查主目标与退出条件 | 若目标抽取错会持续错误，用户撤销必须能生效 |
| memory 召回 | 找回跨时段约束和已完成结果 | 错误/过期召回会重新引入旧要求 |
| compact 交接摘要 | 控制窗口，保留有效要求与状态 | 有损且可能漂移，需要保留来源和回归测试 |
| 独立验收/检查点 | 防止模型自称完成但没有证据 | 增加耗时，验收器也不能无限相信模型判断 |

核心是分离“用户目标”“助手计划”“真实执行结果”。用户问进度不会取消原目标，助手提出的下一步也不自动构成额外授权。长期目标在新 Turn、恢复后、compact 后、关键里程碑和最终完成前检查即可；每个 token 重复提示只会浪费预算。研究中的多轮失败说明早期错误假设值得主动重新审视，不能仅压缩助手最后一段总结。[LLMs Get Lost In Multi-Turn Conversation](https://arxiv.org/abs/2505.06120)

### 本项目的 todo 与一致性

todo 首版支持 list/replace；item 有稳定 ID、内容及 pending/in_progress/completed 状态，列表带 revision。增加、修改和移除事项通过 replace 提交完整列表，使用 expected_revision 校验。取消事项从当前列表移除，旧版本与明确撤销原因保留在事件/对话中，不另加 cancelled 状态。completed 只表示清单状态，是否验证完成通过外联执行/验证事件和验收判断，不暗加证据字段。默认 session 隔离，模型通过 Schema 调用，不能靠解析自然语言里的“已完成”偷偷修改 todo。

todo 修改由 Session owner 追加事件，写盘成功才更新 reducer；并发更新用 expected revision 检查，旧版本冲突返回明确工具错误，不能 last-write-wins 丢失用户修改。Hook 拒绝时不更新状态，post hook 失败也不回滚已成功修改或再执行一遍。

compact 保留当前有效目标、todo 与完成证据；恢复从日志归约 todo，不依赖摘要猜清单。为 cache 只追加状态变化，不每轮替换历史 todo 消息。长任务同时受 `max_steps_per_turn`、wall time、token/cost 和重复失败限制；达到限制记录真实的 limited/failed 状态，不伪造完成。

测试应覆盖中途增改/撤销目标、进度追问后继续、todo 修订冲突、重复 request 去重、恢复不重复副作用、compact 不复活取消项，以及“测试未运行却声称完成”的验收失败。

## 2. 每天早上 9 点根据昨天聊天复盘，怎样设计？

面试回答：调度器负责何时启动，Runtime 负责读哪些已授权聊天并生成结果，通知服务负责送达。模型不应通过长时间 sleep 实现日历调度。

配置持久化包含 `schedule_id/user_id/timezone/local_time/scope/prompt_version/enabled`。例如时区 Asia/Shanghai，每天本地 09:00 触发；“昨天”是用户时区的 `[昨日00:00, 今日00:00)`，转换 UTC 查询事件。不能用“过去24小时”代替自然日；其他时区要明确夏令时重复/缺失时刻策略。

一次执行的幂等键为 `(schedule_id, target_local_date, prompt_version)` 或业务选择的固定日期键；版本改动是否允许重做必须明确。调度器持久化 due run，worker 领取带租约的 job，生成完成后保存摘要 artifact 与输入事件范围，再创建 notification outbox。掉线后重试已有 run，不无条件生成第二份。对同一天聊天后补/编辑，选择固定快照版本或显式重跑版本，避免同一个 run 的输入悄悄变化。

读取范围必须明确是单 session 还是用户授权的多个 session；不能因“昨天聊天”就擅自读取同账号所有空间。按事件发生时间与已确认状态选取用户对话及必要工具结论，过滤 token delta、重试噪声和 secrets。对很长的一天分段摘要，最终保留主题、完成事项、未决问题和下一步，不给未来自动执行权限。

生成任务与活跃聊天可用独立后台执行空间；结果作为通知送入原 Session mailbox，在安全边界接入。当前 session busy 时不抢写 context。用户不在线也要先保存结果，稍后展示。外部渠道发送需既有授权；通知携带稳定 ID，接收端去重。外部渠道若不支持幂等，只能承诺至少一次尝试，不能保证端到端 exactly-once。

边界策略要明确：停机错过 9 点是否补跑、最多补几天、上次仍运行时跳过还是排队、无聊天是否生成“昨日无记录”、取消后已运行任务如何停止、摘要失败如何重试。成熟调度系统将 overlap 与 backfill 作为明确策略，本项目可借鉴其语义但不依赖其实现。[Temporal Schedules](https://docs.temporal.io/schedule)

测试用可注入时钟：跨午夜、夏令时、重启补跑、重复触发、租约过期、生成成功但通知失败、取消与触发竞态、无聊天、越权 scope、正在 busy 的 session。断网后应恢复送达已生成摘要，而不是重新对同一天无限调用模型。
