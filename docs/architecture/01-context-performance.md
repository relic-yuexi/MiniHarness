# 模块一：Context / Performance

调研日期：2026-09-12。本文区分公开资料的结论与 MiniHarness 的设计选择；设计尚不等于已实现或已通过测试。

## 1. 第一轮长窗口或多模态输入，如何把 5–10 秒压到 2 秒？

面试回答：先明确 2 秒指“界面确认收到”“首个模型输出 token”，还是“首个有用答案”。前者可由客户端及时反馈做到；后两者受上传、预处理、网络、服务排队、模型 prefill 和推理耗时影响。面对任意冷启动长输入，不能仅靠开启 stream 就保证真实 TTFT 稳定在 2 秒内。

先打点，测上传结束、请求发出、响应头、首个流事件、首个可见文本和完成时间，分别看 p50/p95，并按输入长度、模态、缓存命中、模型和地区分桶。SDK 的第一个事件可能只是元数据，不能把它当首个答案。

低成本实施顺序是：

1. 文件上传后立即在后台解析、分块和建立索引；把工作移动到用户点击发送之前。输入确实已到达才展示“已接收，正在读取”，不能伪造模型判断。
2. 常驻连接、复用 HTTP client；避免在一次回答前串行执行多个分类、重写、检索模型。独立检索和预处理可以并行。
3. 固定 system、工具 Schema 和历史前缀；变化内容放后面。缓存对重复前缀有效，首次出现的新长文仍要付出冷 prefill，预热只是转移而非消灭成本。OpenAI 官方说明缓存依赖精确前缀；Anthropic 提供显式缓存控制，具体 TTL 与模型适用性应按配置校验。[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Anthropic Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
4. 根据问题只传必要片段；多模态先用较低成本的缩略图或抽取文本定位，再按需加载高分辨率区域。但若问题要求核对整篇、微小文字或全局关系，不能靠无提示截断换速度。
5. 短简单任务路由低延迟模型；复杂任务先流式提供真实的处理进度，然后产出完整答案。小模型的初步答案必须标明范围，不可编出尚未读取材料的结论。减少无用输出通常改善完成耗时；减少推理预算可能改善 TTFT，但要测质量回退。[OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

验收口径可以是：已完成上传、规定长度与模态范围的热请求，p95 有用文本 TTFT ≤ 2 秒；冷请求单列，并提供 2 秒内的真实接收反馈。若面试要求所有冷长输入都 2 秒，应明确需要限制输入规模、预处理或增加成本，不能给没有条件的 SLA。

MiniHarness 先做到稳定前缀、流式输出和 usage/延迟 trace；不在最小项目里建设多模态索引服务。记录 input/output、cache read/write、reasoning token 的原始字段与规范字段；未知用 null，不能当 0。缓存 token 是输入的构成项还是独立计费项取决于 Provider，不把所有字段直接相加。

## 2. 连续聊 200 轮，context 快满了，怎样压缩且保持流畅？

面试回答：压缩目标是维护“当前有效任务和可继续执行的状态”，而非生成聊天流水账。先区分活跃工作集、不可变事件历史和长期 memory。历史落盘不等于每轮都发给模型；压缩改变 ContextView，不覆盖 session.jsonl 中的旧记录。

本项目采用用户给定的中文交接摘要 prompt，保留目标、增改撤销关系、约束、验收条件、已完成且有证据的动作、结果未知的操作、必要路径/ID 和下一步。保留决策依据而非完整思维链。最近若干完整 Turn 原样保留；旧摘要与更早已闭合 Turn 重新摘要，不能切开 tool call/result 配对。

论文发现多轮任务中模型会过早假设、依赖错误的早期解法，导致后续难以恢复。因此摘要必须从用户要求和工具证据重新整理，不能只相信最后一条 assistant 自述。该论文并未证明任意摘要 prompt 都能解决问题，效果还需项目测试。[LLMs Get Lost In Multi-Turn Conversation](https://arxiv.org/abs/2505.06120)

### 预算与触发

按用户要求，初版文本估算 `ceil(len(text.encode('utf-8')) / 4)`，对序列化后的实际消息和工具定义估算；这是近似值，中文、代码及不同 tokenizer 的误差需用真实 usage 校准。图片不能用文件字节/4估算，未支持模态应拒绝或使用专用估算器。

定义 W 为模型窗口，C 为包含 system/tools 的当前上下文，U 为尚未计入的本次输入，P=2048 为压缩 prompt 预留，S=8192 为摘要输出预留。用户给定的核心条件可写为：

`C + U + P + S < 0.8 * W`

这应作为“仍有空间进行压缩”的提前边界，不要等不等式严重失效才发压缩请求。另做正常请求检查 `C + U + R_normal < floor(0.8*W)`，压缩请求检查 `C_compact + P + R_compact < floor(0.8*W)`；等于阈值也触发保护。R_compact 至少覆盖目标摘要，并按具体模型核对 reasoning 是否包含在 max output 内；不能既漏算也双算。设低于危险线的触发水位，压缩后设回落水位避免每轮反复 compact。P 的实际文本估算大于 2048 时用实际值。

若超大单条输入、工具结果或配置错误使压缩本身也放不下，首版返回可恢复的超限错误，提示分块读取或减少显式输入，不发送超窗请求。按完整 Turn 分段摘要后再合并属于可选的显式降级扩展，不是首版自动必备能力；单个不可分割输入须分块读取或拒绝该请求。保留预算上限和最大压缩尝试次数；不能为了压缩无限循环。

### 原子提交与冲突

在 Step 工具批次闭合的安全边界捕获 `cutoff_event_seq`、源消息 hash 和旧 epoch，发无工具的压缩请求。摘要完整、预算合格且基础校验通过后，追加 `compact.committed`，记录覆盖范围和新 epoch，关键写盘成功后切换内存 ContextView。失败或空摘要不改变旧 view。压缩期间新消息仅入队，commit 后再接入；不把晚到的新消息悄悄丢入已截断范围。CAS 检查 context version 和被压源前缀，不能要求最新日志 seq 不变，否则正常 enqueue 也会误触发冲突。源范围若被不允许的状态变化影响，则丢弃该候选并重做，不覆盖后续事件。

compact 是明确允许重建前缀的操作；其他操作只追加新消息。新 epoch 为 `system + 固定 tools + 交接摘要 + 保留的近期完整消息 + 新输入`。摘要是受信任压缩流程生成的历史数据，不应获得修改 system 规则的权限。原始历史可供用户审计，但摘要必须独立可用，不假定模型能自行访问被移除历史。

### 测试验收

用 200 轮合成对话检验仍有效要求、撤销要求、数字路径、工具事实、纯文本/带工具追问和 todo 状态；设置对照分支比较 compact 前后的任务继续结果。注入空摘要、超长摘要、超时、磁盘失败、压缩期间 steer、工具未知结果和超大单 Turn。确定性测试检查预算与消息配对；真实 LLM 测试检查要求保持和任务成功率，不用摘要字符串完全相等作为质量标准。
